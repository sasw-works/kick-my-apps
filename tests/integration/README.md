# Integration tests (real Postgres, real app)

These run the actual app against a local PostgreSQL, through the real sign-in flow, so the SQL that
protects user data is *executed*, not just read. They are not part of the Next.js build.

| File | What it proves |
| --- | --- |
| `isolation_test.py` | Two users can't see, change, or delete each other's reports/comparisons; legacy owner-less rows are invisible; admin access; account deletion removes everything. |
| `hardening_test.py` | Sign-in code attempt limit holds under parallel guesses; codes are single-use; send-code and analyze rate limits (including atomicity under concurrency). |
| `pulse_check_test.mjs` | Unit test of the Pulse alert logic (rating drop/rise thresholds, negative-review bursts relative to an app's own normal, new-version detection, an unreadable review feed vs. genuinely nothing new, atomic claim under concurrency, fair rotation, data pruning) against a real Postgres with FAKE Apple responses -- no network. `POSTGRES_URL=... node tests/integration/pulse_check_test.mjs`. |
| `pulse_api_test.py` | The Pulse API end to end against the real Apple App Store (real search, real app data) and a real Postgres: add/list/pause/delete, ownership isolation between two users, the Free plan's 1-monitor limit, duplicate detection, manual-check cooldown, cron auth. |
| `secret_leak_test.py` | A malformed AI key (pasted several times / with newlines) or missing keys never puts a secret or server internals in a response or in the server log; members get a generic message, admins a redacted detail. Needs network (talks to the real providers with obviously fake keys). |
| `unsubscribe_test.py` | The full subscription lifecycle against a real Postgres: subscribe/list/delete (owner-scoped, like everything else), the token-based no-login unsubscribe link (GET only looks it up, DELETE actually removes it, reusing a link is graceful), and that one subscriber's token can't affect another's row. |
| `plan_limits_test.py` | Monthly report/comparison limits (Free plan: 2 reports, 1 comparison) against a real Postgres: blocked exactly at the limit (not before/after), the plan-limit check runs before the AI is ever called, owner-scoped (one user's usage never affects another's), resets next calendar month, and /api/account/usage returns real current numbers. |
| `admin_exempt_test.py` | Admins are exempt from every plan limit (reports, comparisons, Pulse monitors) via app/lib/plans.js, while a regular account is still genuinely limited -- the exemption doesn't accidentally disable enforcement for everyone. |
| `audit_fixes_test.py` | A pre-Paddle audit pass: account deletion now also removes Pulse monitors (and their cascaded snapshots/reviews/alerts) instead of orphaning them; account/me and update-name reject the instant a session's underlying user row is gone rather than silently no-op'ing; /api/history enforces the report limit directly (not just /api/analyze, which only gates the AI call) so bypassing analyze can't write unlimited reports; search-app and app-icon (both public, no sign-in) are now IP rate-limited; avatar upload, account deletion, and the public token-based unsubscribe link are now rate-limited too (previously the only unprotected mutations). |
| `share_links_test.py` | Public read-only report links: only the owner can create / read / revoke one (another user and anonymous get 404/401), the link is an unguessable 32-char token that's idempotent until revoked, the public page opens with no sign-in without leaking the owner's email and is noindex / disallowed in robots, revoking (or deleting the report or the account) kills the link at once, a new share issues a new token, the token never appears in the normal report API, and management is rate-limited. |
| `tasks_test.py` | The Tasks feature (per-app to-do list built from the latest report): reports of one app group into one project (by store id, even after a rename), statuses (to do / done / won't do) persist and are owner-only (another user 404, anonymous 401), unknown categories/statuses refused, a re-scan keeps "won't do", puts an item ticked "done" back to to-do as "came back" if the new scan still flags it, flags new issues, lists scan-confirmed fixes, the report page shows statuses read-only, earlier per-report ticks are migrated once, account deletion clears them, rate-limited; also the score history the trend chart uses (same app only, oldest first, per-lens scores, never another user's reports). |
| `pulse_kinds_test.py` | Monitored apps are one kind of thing that is "mine" or "other" (someone else's app), against the real App Store: defaults (alerts on for mine, off for other), the one monitor list and the single plan limit (Free 2, counting both kinds), the compare view (only for "mine", only other apps in the same store and country, real rating/version/gap), switching kind and alerts (PATCH), ownership (other user, anonymous), admin exemption, and cleanup. |
| `store_visuals_test.py` | The "store visuals" review (AI look at the store icon and screenshots), against a local stand-in for Gemini and real App Store / Google Play images (it starts its own app server on port 3112): generic 503 with no AI key, real images sent to the model (icon first), a messy model answer sanitised (ratings, out-of-range and duplicate screenshot numbers, caps, extra fields), the review saved and re-read without another AI call, App Store and Play reports, owner-only (other user, anonymous, even an admin), reports with no store link, provider failures and non-JSON answers (generic 502, the earlier saved review kept), and the 10/hour limit. |
| `store_visuals_unit_test.mjs` | Unit test of the helpers: which image URLs may be fetched (store image hosts only; look-alike hosts, http, ports, credentials, private IPs refused), downsized image URLs, the prompt, and sanitising / parsing the model's answer. `node tests/integration/store_visuals_unit_test.mjs`. |
| `release_impact_api_test.py` | "Did the release help?" for a monitored app, with seeded data (no network): per-version review comparison, verdict, moved topic, store average before/after, tasks marked done around the release (real titles; "won't do" excluded), a thin comparison is "unclear", only for "mine" apps, no mix-up between apps or users even with the same app id, anonymous 401. |
| `release_impact_test.mjs` | Unit test of the comparison: versions in order seen, verdicts (better / worse / flat) only with at least 8 reviews on each side, moved topics, the task window around a release, garbage input, the 6-version cap. `node tests/integration/release_impact_test.mjs`. |
| `review_topics_api_test.py` | Complaint topics from stored reviews and the one-click task, with seeded data (no network): exact counts over 1-3 star reviews only, the 3-mention minimum, "no report yet" (409), adding (idempotent) into the same project a report of the app uses, the task built server-side with real counts and showing in Tasks / the overview / exports, marking it done (made-up keys refused), only for "mine" apps, no mix-up between users with the same app id, and account deletion clearing it. |
| `review_topics_test.mjs` | Unit test of the topic counting: English and Turkish phrasing, praise not counted, trend from the newer vs older half, false positives ("loads", "slowpoke"), garbage input, and the task a topic becomes. `node tests/integration/review_topics_test.mjs`. |
| `play_store_test.py` | Google Play support, against the real Play store: search (Play only, App Store default, both tagged, bad value falls back), monitoring a Play app by package id or by link (real rating, rating count and recent written reviews saved; duplicate 409; unknown package 404; junk 400), competitors must be in the same store as the app (both directions), competitors hidden from the list, and another user can't see it. |
| `play_store_unit_test.mjs` | Unit test of the Play helpers: package-id and link parsing (hostile input refused), store told apart by id, project keys for Play links, mapping of scraper output (version "varies" -> null, ms timestamps, clamped text, derived review ids). `node tests/integration/play_store_unit_test.mjs`. |
| `issue_export_api_test.py` | Task exports for Linear / Jira / GitHub and the App Health badge, with seeded data (no network): right type and download name per format, only open tasks, md and csv unchanged, unknown format 400, other users' projects 404, anonymous 401; and the badge of a shared report (score only, nosniff + restrictive CSP + short cache, nothing else exposed), bad or unknown tokens giving a 404 "unavailable" badge, and "Stop sharing" killing it at once (a new link gets a new token). |
| `issue_export_test.mjs` | Unit test of the Linear and Jira CSVs (columns, priorities, open tasks only, line breaks kept, formulas defused), of the GitHub script (valid shell, runs against a fake `gh`: one issue per open task, every title and body byte-for-byte even with quotes, `$(...)`, backticks, leading dashes and newlines, nothing executed from report text) and of the badge SVG (colours, invalid scores never reach the markup). `node tests/integration/issue_export_test.mjs`. |
| `rival_changes_api_test.py` | The "what your rivals did" feed, with seeded data (no network): only the signed-in user's other-people's-apps (never her own app, never another user's), newest first, 7 / 30 day periods with bad values falling back, app name and link per row, the number of rivals watched, one app's own log in its page data, owner-only, and deleting a monitor taking its log. |
| `rival_changes_test.mjs` | Detection of rival listing changes (version + notes, name, icon, screenshots, price) and the change log written at each check, with fake store responses: icon/screenshot comparison ignoring size and cache parameters, nothing logged on the baseline, on unchanged checks or on the first check after the upgrade (old snapshots), logged even with alerts off, no duplicates, own apps excluded. `node tests/integration/rival_changes_test.mjs`. |
| `release_notes_api_test.py` | The release-notes writer and the "it's fixed" reviews list, with seeded data and a local stand-in for Gemini (own server on port 3112): only tasks done since the last release (report findings and review tasks, titles from the server), keys outside that list ignored, only the picked tasks and her own note reaching the model, language, App Store 4000 / Google Play 500 limits, 503 without a key, 502 on provider trouble or an empty answer, input checks, the hourly limit, owner-only and own-app-only; and the reviews of a topic marked done (refused with 409 until it is done, 1-3 star only, never another user's). |
| `release_notes_unit_test.mjs` | Unit test of the release-notes prompt (only-listed-changes rule, task titles inside data markers, clamped inputs, store limits) and answer cleanup (preamble, markdown, bullets, cutting to the limit). `node tests/integration/release_notes_unit_test.mjs`. |
| `notifications_api_test.py` | Account webhook settings (Slack / Discord / generic), against a local receiver (own app server on port 3112, once with SSRF rules active, once with the test-only private-host switch): sign-in required on every verb, http / loopback / private / metadata / credential URLs and a Slack kind on a foreign host refused, kind detected, the full URL never returned (masked), one channel per account, test message delivered in the right shape and to the right user only, receiver failure -> 502 with a plain message and status shown, test rate limit, and account deletion removing the channel. |
| `notify_test.mjs` | Delivery of Pulse alerts and the weekly digest to the channel, with fake Apple responses and a local receiver: baseline sends nothing, one message per check, the monitor's alerts switch silencing it, no channel / other users' channels untouched, and a failing or unreachable receiver never breaking the check. `node tests/integration/notify_test.mjs`. |
| `webhook_unit_test.mjs` | Unit test of webhook URL rules (https only, no credentials, no localhost / private / metadata / mapped-IPv6 addresses, Slack and Discord hosts), payload shapes per service, and delivery: no redirects followed, timeouts, no receiver details in errors. `node tests/integration/webhook_unit_test.mjs`. |
| `reply_draft_test.py` | The "draft a reply to this review" endpoint, against a local stand-in for Gemini (no real AI key; it starts its own app server on port 3112): a generic 503 with no key names when no AI is configured, a cleaned-up draft, tone defaults by star rating, the review text reaching the model only inside data markers (and the key only in a header), owner-only and own-app-only (another user, a missing review, a competitor's review all 404; anonymous 401), input checks, fallback to the second model, generic 502 (no provider detail or key) when everything fails, empty answers rejected, and the 30/hour limit. |
| `reply_draft_unit_test.mjs` | Unit test of the reply prompt (tone, flattened review inside data markers, injection text kept out of the instructions, clamped inputs, no-invented-fixes rule) and of cleaning the model's answer (quotes, markdown, preambles, length). `node tests/integration/reply_draft_unit_test.mjs`. |

| `task_export_test.mjs` | Unit test of the Tasks export (Markdown checklist / CSV): quote and newline handling, a BOM so Excel reads UTF-8, spreadsheet-formula neutralization (cells starting with = + - @), markdown/HTML escaping, safe file names. ## Run
```sh
# 1. Postgres with a database `kma_test` and role kma/kma (see the psql lines in the history of this file's commit)
# 2. use the stand-in driver and build
tests/integration/setup-shim.sh enable
npx next build
POSTGRES_URL=postgres://kma:kma@127.0.0.1:5432/kma_test AUTH_SECRET=test AUTH_TRUST_HOST=true \
  ADMIN_EMAILS=admin@x.com npx next start -p 3111 &
# 3. run
python3 tests/integration/isolation_test.py
python3 tests/integration/hardening_test.py
POSTGRES_URL=postgres://kma:kma@127.0.0.1:5432/kma_test node tests/integration/linking_test.mjs
# 4. ALWAYS restore the real driver afterwards
tests/integration/setup-shim.sh disable
```
The suites truncate their tables at the start, so they are safe to re-run. Never point them at a
real database.
